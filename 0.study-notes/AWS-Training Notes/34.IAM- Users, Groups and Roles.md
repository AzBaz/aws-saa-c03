 [[0. AWS-SAA-Training Overview]]  

**AWS vs Customer** Customer is responsible for security "in" the cloud.
AWS is responsible for security "of" the cloud (hardware, regions, availability zones, edge locations, physical infrastructure).

Key examples:
- **EC2 (IaaS):** You must patch the OS, manage middleware, runtime, data, and applications.
- **RDS (PaaS):** AWS patches the OS; you manage your data and application layer.
- **S3 (SaaS):** You don't manage any OS patching, AWS handles nearly everything beneath the data.

**The Root Account**- When you first create an AWS account, an AWS Root Account is created automatically.
Has full, unrestricted control over every resource in the account. no policy can limit it.
Accessed by logging in with the email address used to create the account + a password + MFA (if configured).
The root account is identified by an Account ID (a 12-digit number) visible in the top-right of the IAM console.
*Root Account Best Practices*
- **Do NOT use the root account for day-to-day work.** Only use it for account-level administrative tasks (e.g., billing, creating the first IAM admin user).
- **Do NOT create access keys for the root account.** This is strongly discouraged by AWS. If the root access keys are compromised, the attacker has unlimited access to everything.

**IAM** = Identity and Access Management. IAM is AWS's global (not region-specific) service for controlling who can do what within an AWS account. It manages authentication and authorization for all AWS resources.
IAM is free there is no charge for creating users, groups, roles, or policies

**User**- Entity that can access AWS resources. 
Created by ROOT user. User with proper IAM permissions
By default **Denied everything**  no permissions by default

*User Console Access*
Users who need to log into the AWS Management Console need:
Account ID or Alias, the 12-digit account number, or a custom alias you can configure
IAM username
Password
MFA (if configured strongly recommended)
Password Policy:
AWS enforces a minimum password policy by default (minimum 8 characters, mix of character types).
Custom password policies can be configured under IAM ->Account Settings -> Password Policy. Configurable options include: minimum length, character requirements, expiration/rotation periods, and prevention of password reuse.

**Programmatic Access -Access Keys**
For *CLI, SDK, or API* access (non-console), users use Access Keys.
An Access Key has two parts:
Access Key ID: the "username" equivalent (public part)
Secret Access Key: the "password" equivalent (private part, shown only once at creation)

Demonstrated in the video: Using *aws configure* in the Windows CLI to set up programmatic access, you paste in the Access Key ID and Secret Access Key, and then all aws CLI commands use those credentials to authenticate.
Types of Access Keys:
*Static*- Fixed key pair assigned to a user- Dev/test environments only
*Dynamic*- Temporarily generated via STS (Secure Token Service) -Production environments

Static access keys are *dangerous in production* because:
The creator of the keys also knows them (two parties have access).
They cannot be rotated automatically.
If compromised, the entire programmatic access surface is exposed until manually revoked.

**IAM Groups**- Used to organize users based on: Department, job Role, Functions, Title
Specify permissions for multiple users at the same time
A group is not an identity, it cannot be referenced as a principal in a policy to assume roles.
Users in a group inherit the group's permissions (policies attached to the group apply to all members).
*A user can belong to multiple groups.*
Permissions can be managed at the group level instead of individually, far more scalable.

**IAM Roles** - A type of IAM identity, similar to user, BUT has permissions/policies that determine what it can do. 
Used by *anyone or anything* that needs to assume the role needed to do something *temporarily*
	Person, Application or EC2 instance
	Role permissions are in effect for that temporary period. 

Note: Roles are so critical in AWS that you are tested on them in every single level of AWS certification
*Roles* provide short term credentials for accessing AWS resources, once expired -> Access is DENIED
Credentials NOT stored with the user, OS, application, etc.
	Generated dynamically and provided to the user when requested. 
Advantages: 
	No need to embed credentials without having to create IAM users
	No need to rotate or manage the lifetime of a key.

*Roles Usage Scenarios:*
*Identity Federation*: Users from an external identity provider (e.g., Active Directory, Google, SAML) assume a role when logging in. They authenticate externally, then get AWS permissions via the assumed role.
*Cross-Account Access*: Allow users or services in one AWS account to access resources in another account without creating duplicate IAM users.
	Scenario: A Production Account admin wants to allow developers in a Development Account to read/write to an S3 bucket called "productionapp".
	Step-by-step flow:
	1.Production Account Admin creates a role called "UpdateApp" that grants read/write access to the "productionapp" S3 bucket.
	2.Admin grants members of the Developers group (in the Dev Account) permission to call "sts:AssumeRole" on the "UpdateApp" role.
	3. A Developer user requests access to the "UpdateApp" role.
	4. AWS STS returns temporary role credentials to the developer.
	5. The developer uses those role credentials to update/write to "productionapp", all actions governed by the role's permissions.
	*Key insight*: No IAM user is created in the Production Account for the developer. Instead, a role is assumed across account boundaries using STS.
	
*Elevating a User's Privileges*: Temporarily grant a user elevated permissions by having them assume a role with broader access (similar to Linux sudo).
*Granting a Resource Access to Another Resource*: An EC2 instance assumes a role to read/write from S3, send messages to SQS, etc.
*Granting an App Access to a Service*: An application running on EC2 needs to interact with DynamoDB, CloudWatch, etc. done via role assumption, not static keys.
