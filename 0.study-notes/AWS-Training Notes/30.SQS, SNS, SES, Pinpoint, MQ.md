**Simple Que Service (SQS)**- Fully managed queue service; 
Decouple and Scale: *Microservices,  Distributed Systems, Serverless Apps*
Rather than a frontend directly pushing to a backend (which risks overload, messages get lost, and never processed), SQS sits in between: the frontend *pushes* messages into the queue, and the backend *polls and pulls* messages from it.

**Serverless Architecture Example**
A common pattern: Application -> API Gateway -> SQS ->  Lambda (polls/pulls) -> DynamoDB. Lambda can also push to a second SQS queue, which another Lambda processes.

**Queue Types**
Standard Queue
	Default queue type
	Provides nearly an *unlimited* number of transactions/sec
	Guarantees a message is delivered at least once
	Provide best effort ordering
		Messages can be delivered out of order
FIFO Queue
	Provides order delivery (never out of order and NO duplicates)
		First-In-First-Out
	Exactly once processing and delivery- no duplicates at all
	Limited to *300* transactions/sec

**SQS Key Message Properties**
Messages are limited to 256KB in size
Messages will be kept in the queue by default for 4 days or until they have been pulled- configurable 1min to 14days
Once pulled the Visibility Timeout kicks in
	The total time the message will still be in the queue but invisible once it has been pulled
	If message is processed before the visibility timeout expires, the message is deleted
	If the message is not processed before the visibility timeout expires, the message becomes visible so it can be pulled again
	Default is 30 secs... Max is 12 hrs. 
Configure your code to delete message from the queue once it was successfully processed.  

**Polling Types**- Act of backend polling from the queue
*Short Polling*- Will return a response immediately regardless of there being a message in the queue or not.
since each poll costs money regardless of the being a message returned or not, this can become expensive
*Long Polling*- Will return a response immediately only if there is a message in the queue, if there is NO message in the queue it will wait until one arrives or until the Receive Message Wait Time expires
	Will reduce the costs associated with polling when a queue is lightly used. 

**Dead Letter Queues (DLQ)**-  Messages that are *never processed* (never pulled) are deleted after the retention period expires
To preserve failed/unprocessed messages, use a *Dead Letter Queue (DLQ)*
DLQs receive messages from other queues that could not be processed or pulled after a specified number of attempts
Excellent for *troubleshooting and debugging* why your application failed to pull or process a message

**Simple Notification Service (SNS)**- Fully managed Notification Service
Allows you to setup, operate, and send notifications from the cloud
Highly scalable, available, flexible, cost-effective message publication/subscriber service
Easily send messages to multiple recipients
**How It Works**
	 *Publishers* send messages to an SNS *Topic*
	 A *Topic* is a logical access point and communication channel that endpoints subscribe to
	 SNS *pushes* the message out to all *Subscribers* who have subscribed to that topic
	 Subscribers can be: Mobile Devices, Lambda Functions, SQS Queues, Web Servers, Email Addresses, SMS messages
**Subscription Filter Policies**
	Subscribers can apply a *filter policy* (JSON-based) to receive only a subset of messages
	Filter scope applies to either *Message Attributes* or *Message Body*
	Example JSON filter: keys with allowed values defined as arrays
**SNS Retries**- A delivery policy defines how SNS retries the delivery of messages when server-side errors occur
	When the delivery policy is exhausted, Amazon SNS stops retrying the delivery and discards the message, unless a dead-letter queue is attached to the subscription. 

**Simple Email Service (SES)**- Highly available and scalable email service designed to help marketing and application teams send emails to customers (i.e. Marketing, Notifications, Transactional)
Only pay for what you send
Can receive emails as well: 
	Incoming emails can be delivered to S3
	Receiving emails can trigger Lambda functions and SNS notifications. 

**Amazon Pinpoint** - enables you to engage with your customers across multiple messaging channels using customer data to drive personalized campaigns.
	Push notifications
	In-app notifications
	Emails
	Text messages (SMS)
	Voice messages
	Messages over custom channels
**How It Works**
Pinpoint ingests Customer and Usage Data, then manages: Audience Management -> Campaign and Journeys -> Channels -> collects Engagement Data. It also handles Transactional Messages (automated real-time messages)
	Setup is simpler than SNS.
**Integrations**
Pinpoint can deliver and connect with: *Amazon Redshift, Amazon S3, Amazon EC2, AWS Lambda, Amazon EMR*, and other AWS services for analytics and delivery.

**Amazon MQ**-  Managed Message Broker Service (intermediary system) that provides communication between software applications and components using various programming languages, operating systems, and formal messaging protocols (e.g., AMQP, STOMP, MQTT, OpenWire).
	It is the go-to choice when **migrating existing applications** that already use message brokers avoiding the need to re-engineer for SQS/SNS.
Supported Broker Engines
	Apache ActiveMQ
	RabbitMQ

**Architecture Options**

| Engine       | Deployment Option  | Notes                           |
| ------------ | ------------------ | ------------------------------- |
| **ActiveMQ** | Single-instance    | Single broker node              |
| **ActiveMQ** | Active/Standby     | High avail. failover pair       |
| **ActiveMQ** | Network of Brokers | Multi-broker mesh               |
| **RabbitMQ** | Single-Instance    | Single broker node              |
| **RabbitMQ** | Cluster            | Distributed, replicated cluster |
## Key Comparisons & Exam Tips

| Service       | Type                     | Direction                                  | Best For                                            |
| ------------- | ------------------------ | ------------------------------------------ | --------------------------------------------------- |
| **SQS**       | Queue                    | Pull-based (consumers poll)                | Decoupling services; async processing; buffering    |
| **SNS**       | Pub/Sub                  | Push-based (SNS pushes to all subscribers) | Fan-out notifications to multiple endpoints         |
| **SES**       | Email                    | Send & Receive                             | Marketing, transactional, and notification emails   |
| **Pinpoint**  | Multi-channel engagement | Push (campaigns + journeys)                | Customer engagement analytics & targeted messaging  |
| **Amazon MQ** | Message Broker           | Protocol-based (AMQP, STOMP, etc.)         | Migrating apps that use traditional message brokers |

**SQS vs SNS:** SQS uses **polling** (consumers pull); SNS uses **push** (subscribers receive automatically). **SQS vs Amazon MQ:** Use SQS for new cloud-native apps; use Amazon MQ when migrating legacy apps that rely on standard messaging protocols. **SNS + SQS Fan-Out Pattern:** Combine both SNS pushes to multiple SQS queues simultaneously, allowing parallel processing by different consumers without message loss.
