**Amazon CloudWatch** - A monitoring service for AWS resources; application you run on AWS. 
You can: 
	Collect and track metrics
	Collect and monitor log files
	Set alarms; Gain system-wide visibility into resource utilization, application performance, and operational health.

![[Pasted image 20260708111412.png]]

CloudWatch also works for on-premises resources, not just AWS-native ones, if you set it up.
Emphasized CloudWatch is more than metrics= it's the centralized place for metrics, logs, alarms, and dashboards across every AWS service.

**CloudWatch Metrics** - Data about the performance of your resources and applications. 
Time ordered set of data points. 
- Metrics always live in the same AWS region as the resource they belong to (console UI now lets you view other regions without switching, but data is still regional).
- Metrics cannot be deleted and persist for 15 months even after the resource is terminated.

**CloudWatch monitoring Tiers**
- Basic (free, 5-minute intervals)
- Detailed (paid opt-in, 1-minute intervals)
- Custom (you push data at whatever interval you code for, e.g., 15–30 seconds).

**CloudWatch Agent** - get additional metrics and log files from your servers.
- For EC2 Instances
	- Collect internal system-level  metrics
	- Retrieve custom metrics from your applications or services
	- Collect logs from either Linux or Windows Server
- For On Prem
	- Collect system-level metrics
	- Retrieve custom metrics from your applications or services
	- Collect logs from either Linux or Windows Server. 

**CloudWatch Alarms**
- Keeps track of resource utilization (a single metric)
	- Examples: CPU Utilization, ELB request latency, Storage throughput, SQS queue length, charges to your AWS bill, custom applications
- Trigger an action when a threshold is breached
	- Examples: Send an Email, Publish to SNS queue, Stop or Terminate an Instance, Perform and autoscaling Action. 
- Crete Alarms based on: Static Threshold, Metric insight query, Anomaly detection. Log group-metric filter. 

**Alarms Demo**
- Alarm creation flow: select metric -> statistic (e.g., Maximum) -> threshold/comparison -> data points to alarm -> missing-data treatment -> notification action (SNS topic) -> name -> create
- Alarms are built one metric at a time-  there's no "blanket" alarm for an entire resource. Alarms are very specific.
- "Period" length depends on monitoring type: 5 minutes under basic monitoring, 1 minute under detailed monitoring.
	- "number of periods" above 1 (e.g., 3 periods) before triggering: to avoid false-positive/overreactive actions, such as an auto-scaling event firing and reversing itself because of a brief, momentary spike.
- Missing-data handling is metric-dependent: 
	- for something like CPU data going missing, that could mean the instance is overwhelmed (treat as bad); for an error-count metric, missing data is actually good news (treat as "ignore" so it doesn't cause constant false alarms).
- EC2-specific alarm actions (stop/start/terminate) are only available when monitoring per-instance metrics, not aggregate/group metrics.

**CloudWatch Dashboards** - Monitor and Troubleshoot in near real-time
- Customizable home pages you use to monitor your resources in a single view
- Even resources that are spread across different Regions
- Create customized views of the metrics and alarms for your AWS resources
- Sharable with people who have AWS accounts; with people who do not have AWS accounts
*Dashboard sharing*
Share your dashboard and require a username and password (only credentialed users can access)
Share your dashboard publicly (anyone with the link)
Share all your account's CloudWatch dashboards using single sign-on (SSO)

**CloudWatch Logs**- Monitor, Store, Access, Analyze Log files. 
- Centralize the logs from all of your systems, applications, and AWS services
- Easily view them, search them for specific error codes or patterns, filter them based on specific fields, or archive them securely for future analysis
- See all of your logs, regardless of source, as a single consistent flow of events ordered by time
- Also query your logs with a powerful query language, audit and mask sensitive data in logs, and generate metrics from logs using filters or an embedded log format
- Systems and Applications by using their own log files - search for specific phrases, values, or patterns
- VPC network traffic using VPC flow logs - VPC, Subnet, Interface levels
- Logs are stored in S3
- Set up CloudWatch Alarms - notify you of findings; trigger an action

**RECAP of CloudWatch**
- Metrics: understand basic vs. detailed vs. custom monitoring, and remember the CloudWatch agent is required for OS-level/custom/memory metrics.
- Alarms: about getting notified and triggering automated actions (auto-scaling, Lambda, etc.) based on a metric crossing a threshold.
- Dashboards: centralized, shareable visualization - don't forget this exists as an exam topic.
- Logs: centralized log storage/analysis that can itself be turned into metrics and alarms.
- His closing framing: you should be able to confidently tell these four CloudWatch capabilities apart when reading an exam scenario.
