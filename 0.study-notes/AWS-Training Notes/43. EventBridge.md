**AWS EventBridge** - A serverless service for building event-driven applications.
Uses events to connect application components together, making it easier for developers to build scalable event-driven applications.

You can also set up a scheduled triggers and frequency of when the schedule runs. 

I.E. Start and stop a server at certain time, OR run the Lambda Function at certain time. 

**Core components**
- Event bus  pipe that receives events. Three types: Default (AWS service events), Custom (your apps), Partner (SaaS like Zendesk, Datadog, Shopify).
- Rules  match incoming events (via event pattern) or run on a schedule, then route to targets.
- Targets  where matched events go: Lambda, SQS, SNS, Step Functions, Kinesis, ECS tasks, another event bus, etc. (Up to 5 targets per rule.)

**Event routing**
- Event pattern matching  JSON filter on event content (source, detail-type, fields). Only matching events trigger the rule.
- Scheduled rules  cron or rate expressions → serverless cron jobs (e.g., trigger Lambda every hour).

**Key features (exam favorites)**

- Schema Registry  stores event structure; auto-discovers schemas; generates code bindings for typed development.
- Archive & Replay  archive events, replay them later for reprocessing/debugging.
- Input transformation — reshape event data before sending to target.
- Dead-letter queue (DLQ) — send failed event deliveries to SQS.

**EventBridge vs. SNS (common exam distinction)**
- EventBridge: content-based filtering, many AWS/SaaS sources, schema registry, replay, lower throughput, slightly higher latency. Choose for routing/integration logic.
- SNS: high-throughput pub/sub fan-out, message filtering by attributes, lower latency. Choose for simple, high-volume fan-out.

**EventBridge Pipes** (newer, may appear)
- Point-to-point integration: source → (filter → enrich) → target. Connects services with optional filtering and transformation without writing glue code.

**Common use cases**
- React to AWS API calls / resource state changes (via **CloudTrail** for API events).
- Scheduled tasks (serverless cron).
- Decoupling microservices via events.
- SaaS integration without custom polling.
